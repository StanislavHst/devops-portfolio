# Лабораторна робота №3 — монітор Wishlist API

## Завдання 2. Реалізований інструмент

[api_monitor.py](api_monitor.py) контролює доступність локального **Wishlist API** у Docker, який використовує PostgreSQL та Redis. Інтерфейс проєкту працює на `localhost:5173`, API — на `127.0.0.1:8000`.

Джерела проєкту: [Wishlist UI](https://github.com/nromanen/wishlist-ui), [Wishlist API](https://github.com/nromanen/withlist-api).

## Моніторинг реального проєкту

| Endpoint | Очікувана відповідь | Перевірка |
|---|---|---|
| `/health` | HTTP 200; `status=healthy`, `redis=healthy` | Стан API і Redis за JSON-відповіддю |
| `/wishlists` | HTTP 200 | Публічний список; можливе використання Redis-кешу |
| `/openapi.json` | HTTP 200 | Схема API |
| `/docs` | HTTP 200 | Swagger UI |
| `/users/me` | HTTP 401 | Авторизація обов'язкова для захищеного маршруту |

Основна конфігурація: [config/api-monitor.json](config/api-monitor.json). Для кожної цілі задаються адреса, очікуваний код, тайм-аут і поріг часу відповіді. Здоровий проєкт повертає **5 healthy, 0 problems**, код виходу **0**.

`/health` Wishlist може повернути HTTP 200 при несправному Redis. Тому додатково перевіряються поля JSON; `redis=unhealthy` дає окремий результат `unexpected_body`.

Перевірка публічного списку не гарантує поточного з'єднання з PostgreSQL, коли дані повертає кеш. Монітор виконує лише GET-запити та не змінює дані проєкту.

Окремо перевірено реальне вимкнення Redis: `/health` продовжив повертати HTTP 200, але монітор визначив `unexpected_body` та доставив Discord-сповіщення для `wishlist-health`. Після запуску Redis назад усі 5 цілей знову здорові, код виходу `0`.

## Типи збоїв

| Тип | Значення |
|---|---|
| `dns` | домен не перетворився на IP-адресу |
| `connection_refused` | вузол відхилив з'єднання на потрібному порту |
| `timeout` | операція перевищила тайм-аут |
| `certificate` | TLS-сертифікат не пройшов перевірку |
| `unexpected_status` | отримано інший HTTP-код |
| `slow_response` | код правильний, але перевищено поріг часу |
| `unexpected_body` | JSON не містить очікуваних значень |
| `network_error` | інша мережева помилка |

При мережевій помилці виконується рівно одна повторна спроба. Якщо друга спроба успішна, ціль вважається здоровою. Для неправильного HTTP-коду, JSON чи повільної відповіді повтор не виконується.

## Перевірка чотирьох випадків з умови

Окрема конфігурація [failure-scenarios.json](config/failure-scenarios.json) містить неіснуючий домен, закритий локальний порт, домен із простроченим сертифікатом та неіснуючий маршрут **справжнього Wishlist API**, який повертає 404 замість очікуваного 200.

Для TLS-перевірки використано `expired.badssl.com`, оскільки локальний Wishlist працює через HTTP.

Результат 10 листопада 2026 року: **4 різні типи збою, 4 доставлені Discord-повідомлення**, код виходу **1**:

```text
wishlist-dns-failure       dns                  attempts=2
wishlist-closed-port       connection_refused   attempts=2
tls-expired-certificate    certificate          attempts=2
wishlist-unexpected-status unexpected_status    attempts=1
```

## Сповіщення та результати

Особистий Discord-сервер **DevOps Lab Monitor**, канал **#general**, webhook **DevOps API Monitor**. Для кожної проблемної цілі надходить окреме повідомлення: назва цілі, **тип збою**, деталі та адреса. Для здорових цілей сповіщень немає.

Webhook передається через `DISCORD_WEBHOOK_URL`. Локальний секрет зашифрований Windows DPAPI поза Git. [run-monitor.ps1](run-monitor.ps1) підставляє його для Python-процесу. Значення секрету в документації та журналах відсутнє.

Журнал містить час, ціль, результат, тривалість, тип помилки, кількість спроб і `notification=sent` для успішної доставки. JSON-звіт містить підсумок та результат кожної цілі. Журнали і звіти ігноруються Git.

## Автоматична перевірка

**62 тести пройдено** з увімкненим `WISHLIST_LIVE=1`:

- **57 автономних тестів:** конфігурація, помилки значень, класифікація збоїв, retry та відновлення, звіти, коди виходу й Discord. Реальний локальний HTTP-сервер використано для timeout, slow response, статусів і перевірки JSON.
- **5 інтеграційних тестів:** read-only запити до працюючого Wishlist у Docker — health/Redis, список, OpenAPI з реальними маршрутами, Swagger та обов'язкова авторизація.

Без `WISHLIST_LIVE=1` інтеграційні тести пропускаються, тому базовий набір працює без Docker. Автоматичні тести не надсилають повідомлення в Discord.

## Команди запуску

З теки `lab-03`:

```powershell
# Реальний Wishlist: очікується код 0
./run-monitor.ps1

# Чотири навмисні збої та Discord: очікується код 1
./run-monitor.ps1 -Config config/failure-scenarios.json

# Повний набір із працюючим Docker-проєктом
$env:WISHLIST_LIVE = "1"
python -m unittest discover -s tests -v
Remove-Item Env:WISHLIST_LIVE
```

Прямий запуск інструмента: `python api_monitor.py`; довідка — `python api_monitor.py --help`. Для прямого запуску зі сповіщеннями webhook має бути переданий у середовище процесу.

## Обґрунтування рішень

Python і стандартна бібліотека забезпечують запуск без сторонніх пакетів. JSON відокремлює адреси й пороги від коду. Різні типи збоїв дають змогу визначити напрям діагностики. Одна повторна спроба відсіює короткочасні мережеві проблеми. Структурований звіт і коди виходу придатні для автоматичного запуску.

**Connection refused** означає явну відмову — перевіряються процес, порт, firewall і Docker port mapping. **Timeout** означає відсутність завершеної операції за відведений час — потрібна перевірка маршруту, блокувань, втрати пакетів і зависання сервісу.

| Код виходу | Значення |
|---:|---|
| `0` | усі цілі здорові |
| `1` | є проблемна ціль |
| `2` | помилка конфігурації чи аргументів |
| `3` | помилка створення журналу або JSON-звіту |
