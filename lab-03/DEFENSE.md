# Лабораторна робота №3 — монітор Wishlist API

## Завдання 2. Реалізація

[api_monitor.py](api_monitor.py) перевіряє локальний **Wishlist API** у Docker. Усі **16 сценаріїв** зберігаються в одному [config/api-monitor.json](config/api-monitor.json); усі адреси належать `127.0.0.1:8000`.

Проєкт складається з [Wishlist UI](https://github.com/nromanen/wishlist-ui), [Wishlist API](https://github.com/nromanen/withlist-api), PostgreSQL та Redis.

## Сценарії перевірки

| Група | Маршрути | Очікування |
|---|---|---|
| Стан залежностей | `/health` | 200 і JSON `status=healthy, redis=healthy` |
| Публічні дані | `/wishlists`, `/wishlists/0/items` | 200 |
| Документація API | `/openapi.json`, `/docs`, `/redoc` | 200 |
| Авторизація | `/users/me`, `/my-wishlists`, історія статусів | 401 без токена |
| Відсутні ресурси | `/wishlists/0`, невідомий маршрут | 404 |
| Валідація ID | `/wishlists/not-a-number` | 422 |
| Заборонений GET | реєстрація, token, зміна статусу, видалення елемента | 405 |

Очікувані 401, 404, 405 і 422 підтверджують правильну обробку цих запитів. Вони не є збоєм, якщо відповідають конфігурації. ID 0 — відсутній ресурс у поточній локальній базі.

## Обробка проблем

Окремо розпізнаються DNS, відхилення з'єднання, тайм-аут, помилка сертифіката, неправильний HTTP-код, повільна відповідь, неправильний JSON і загальна мережева помилка. При мережевій помилці виконується одна повторна спроба.

Перевірка `expected_json` виявляє несправний Redis, навіть коли `/health` повертає HTTP 200. Реальне вимкнення Redis перевірено: отримано `unexpected_body` і доставлено сповіщення. Redis після перевірки відновлено.

Поточна конфігурація перевіряє лише локальний HTTP API за IP-адресою, тому не відтворює реальний збій DNS або прострочений TLS-сертифікат. Ці класи помилок перевіряються автоматичними тестами. Для повної живої демонстрації чотирьох мережевих випадків з умови потрібне додаткове тестове DNS/TLS-середовище.

## Сповіщення й результати

Особистий Discord-сервер **DevOps Lab Monitor**, канал **#general**. Для кожної проблемної цілі надходить окреме повідомлення з назвою, **типом збою**, деталями та URL. Здорові цілі сповіщень не створюють.

Webhook передається через `DISCORD_WEBHOOK_URL`. Локальний секрет зберігається зашифрованим Windows DPAPI поза Git. [run-monitor.ps1](run-monitor.ps1) підставляє його у середовище Python-процесу.

Журнал містить час, ціль, результат, тривалість, тип помилки, кількість спроб і стан доставки. Структурований JSON-звіт містить підсумок та результати всіх 16 перевірок. Журнали і звіти ігноруються Git.

## Перевірка реалізації

**63 автоматичні тести**: 57 автономних і 6 інтеграційних. Інтеграційна перевірка проходить через усі 16 цілей єдиного JSON на реальному Wishlist у Docker. Тести охоплюють конфігурацію, HTTP-транспорт, типи збою, retry/recovery, JSON, звіти, коди виходу та Discord-повідомлення.

Перевірки виконують лише GET-запити. Користувачі, списки й елементи не змінюються. Публічний список може повертатися з Redis-кешу, тому цей запит не гарантує актуального з'єднання з PostgreSQL.

## Обґрунтування рішень

Python зі стандартною бібліотекою не потребує сторонніх пакетів. JSON відокремлює адреси, очікування й пороги від коду. Одна повторна спроба допомагає відсіяти короткочасні мережеві проблеми. JSON-звіт і коди виходу дозволяють запускати інструмент автоматично.

**Connection refused** означає явну відмову: перевіряються процес, порт і Docker port mapping. **Timeout** означає незавершену операцію за відведений час: перевіряються маршрут, firewall, втрата пакетів, навантаження та зависання сервісу.

| Код | Значення |
|---:|---|
| 0 | усі цілі здорові |
| 1 | є проблемна ціль |
| 2 | помилка конфігурації чи аргументів |
| 3 | помилка створення журналу або звіту |
