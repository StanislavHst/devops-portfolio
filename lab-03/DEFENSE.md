# Лабораторна робота №3 — монітор Wishlist API

## Завдання 2. Реалізація

[api_monitor.py](api_monitor.py) контролює локальний Wishlist API у Docker. Єдиний [config/api-monitor.json](config/api-monitor.json) містить **24 перевірки** для `127.0.0.1:8000`.

Монітор читає конфігурацію, виконує HTTP-запити, визначає тип проблеми, зберігає журнал і JSON-звіт та надсилає повідомлення у Discord.

## Перевірки

- API і Redis: `/health`, HTTP 200 та поля JSON.
- Публічні дані: списки та колекції елементів.
- Документація: OpenAPI, Swagger, ReDoc, OAuth redirect.
- Авторизація: профіль, особисті списки, історія статусів без токена.
- Валідація: некоректні, відсутні, від'ємні й великі ID.
- HTTP-методи: GET на маршрутах, які його не підтримують.
- Маршрутизація: невідомий маршрут.

Склад конфігурації: **20 звичайних**, **1 контрактна**, **3 демонстраційні** перевірки. Очікувані 401, 404, 405 і 422 у звичайних сценаріях означають правильну роботу API.

## Контрактна неузгодженість

`/wishlists/0` повертає 404, проте `/wishlists/0/items` повертає 200. Для вкладеного ресурсу обрано очікування 404 при відсутньому батьківському списку. Монітор визначає `unexpected_status`.

Це перевірка обраного контракту, а не підтвердження вимоги автора Wishlist API.

## Демонстраційні сценарії

| Сценарій | Очікування | Фактичний результат |
|---|---|---|
| Невідомий маршрут | Навмисно задано 200 | 404 → `unexpected_status` |
| Профіль без токена | Навмисно задано 200 | 401 → `unexpected_status` |
| Швидкість `/health` | Навмисно задано до 0.1 мс | Перевищення → `slow_response` |

Сценарії мають `check_kind=demonstration` та префікс **[ДЕМОНСТРАЦІЯ]** у журналі й повідомленні. Вони демонструють роботу монітора та не є багами авторизації, маршрутизації чи підтвердженою проблемою продуктивності Wishlist.

## Перевірений результат

10 листопада 2026 року: **24 цілі, 20 здорових, 4 проблемні**, код виходу **1**. Для кожної проблемної цілі підтверджено `notification=sent`.

Discord: особистий сервер **DevOps Lab Monitor**, канал **#general**. Повідомлення містить ціль, **тип збою**, категорію, деталі та URL.

Webhook передається через `DISCORD_WEBHOOK_URL`. Секрет зашифрований Windows DPAPI поза Git; [run-monitor.ps1](run-monitor.ps1) підставляє його у середовище Python-процесу.

## Запуск і результати

З теки `lab-03`:

```powershell
./run-monitor.ps1
$LASTEXITCODE
Get-Content logs/api-monitor.log -Tail 30
Get-Content reports/api-monitor-results.json
```

У підготовленому VS Code запуск **Wishlist API — 24 checks + Discord** виконується через `Ctrl+F5`. Прямий запуск — `python api_monitor.py`; для сповіщень webhook має бути у середовищі процесу.

Журнал містить час, дію, ціль, статус і спроби. JSON-звіт містить підсумок і результат кожної перевірки. Журнали й звіти ігноруються Git.

## Обробка збоїв

Окремо визначаються DNS, відхилене з'єднання, тайм-аут, сертифікат, неправильний HTTP-код, повільна відповідь і неправильний JSON. Для мережевих помилок передбачена одна повторна спроба.

Перевірка JSON виявляє несправний Redis навіть при HTTP 200. Реальне відключення Redis та доставку сповіщення перевірено; Redis відновлено.

У поточному JSON усі адреси належать локальному HTTP API за IP. Для живого відтворення DNS/TLS-помилок з умови потрібне додаткове середовище.

## Вибір рішень

Python зі стандартною бібліотекою не потребує сторонніх пакетів. Єдиний JSON відокремлює адреси, очікування й пороги від коду.

**Connection refused** означає явну відмову: перевіряються процес і порт. **Timeout** означає незавершену операцію за відведений час: перевіряються маршрут, firewall, навантаження та зависання сервісу.

| Код | Значення |
|---:|---|
| 0 | усі очікування виконані |
| 1 | є проблемна ціль |
| 2 | помилка конфігурації чи аргументів |
| 3 | помилка створення журналу або звіту |
