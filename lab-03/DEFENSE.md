# Захист лабораторної роботи №3 — монітор доступності API

## Що реалізовано

У межах завдання 2 створено консольний інструмент `api_monitor.py`, який:

- читає список HTTP/HTTPS-цілей із JSON-конфігурації;
- перевіряє очікуваний HTTP-код і вимірює час відповіді;
- окремо визначає DNS-помилку, відхилення з'єднання, тайм-аут, помилку сертифіката, несподіваний HTTP-код і повільну відповідь;
- повторює мережеву спробу рівно один раз;
- записує результат кожної перевірки у журнал і структурований JSON-звіт;
- надсилає окреме Discord-повідомлення для кожної проблемної цілі;
- повертає різні коди виходу для успіху, проблемних цілей, помилки конфігурації та помилки запису результатів.

## Структура реалізації

lab-03/

Каталоги `logs/` і `reports/` створюються під час роботи програми та ігноруються Git.

## Чому обрано JSON і стандартну бібліотеку Python

JSON легко перевіряти й редагувати, він не потребує додаткових залежностей. Реалізація використовує `argparse`, `json`, `logging`, `ssl`, `socket` та `urllib` зі стандартної бібліотеки Python. Тому після клонування репозиторію не потрібно встановлювати сторонні пакети.

Webhook не записаний у код або конфігурацію. Він передається через змінну середовища `DISCORD_WEBHOOK_URL`, щоб секрет не потрапив у Git.

## Що показати викладачу

### 1. Репозиторій і Git workflow

Показати, що зміни виконувалися в окремій гілці й потрапили в `main` через pull request:

```powershell
git branch --show-current
git log --oneline --decorate -5
git status
```

Пояснення: прямий push у `main` не використовувався; PR дозволяє перевірити diff і результати перевірок до злиття.

### 2. Довідка інструмента

```powershell
cd lab-03
python api_monitor.py --help
```

Показати параметри `--config`, `--output`, `--log-file`, `--webhook-env` і приклад запуску в кінці довідки.

### 3. Конфігурація

Відкрити `config/api-monitor.json`. У ньому є:

- робочий endpoint;
- неіснуючий домен для DNS-помилки;
- закритий порт для `connection_refused`;
- домен із простроченим TLS-сертифікатом;
- endpoint із кодом `418` замість очікуваного `200`.

Пояснення: URL, очікуваний код, тайм-аут і поріг відповіді налаштовуються без редагування Python-коду.

### 4. Безпечне підключення Discord

Webhook створюється в налаштуваннях Discord-каналу та задається тільки для поточної PowerShell-сесії:

```powershell
$env:DISCORD_WEBHOOK_URL = "<webhook URL>"
```

Значення змінної не потрібно показувати на екрані, друкувати в журнал або додавати в Git.

### 5. Реальний запуск

```powershell
python api_monitor.py
$LASTEXITCODE
```

Очікуваний код — `1`, тому що тестова конфігурація навмисно містить проблемні цілі. У Discord мають з'явитися окремі повідомлення, наприклад:

```text
🚨 API monitor
Ціль: dns-failure
Тип збою: dns
Деталі: DNS: ім'я не вдалося перетворити на IP-адресу
```

Важливо показати, що кожне повідомлення містить поле `Тип збою`, а не лише загальну фразу про недоступність.

### 6. Журнал і структурований звіт

```powershell
Get-Content logs/api-monitor.log -Tail 30
Get-Content reports/api-monitor-results.json
```

У журналі показати час, ціль, статус, тривалість, кількість спроб і `failure_type`. У JSON-звіті показати підсумок і масив результатів.

### 7. Автоматичні тести

```powershell
python -m unittest discover -s tests -v
```

Тести перевіряють класифікацію всіх основних збоїв, одну повторну мережеву спробу, повільну відповідь, несподіваний код і склад Discord-повідомлення. Зовнішня мережа в тестах замінена mock-об'єктами, тому результат стабільний.

### 8. Обробка неправильної конфігурації

```powershell
python api_monitor.py --config config/does-not-exist.json
$LASTEXITCODE
```

Очікується зрозуміле повідомлення без traceback і код виходу `2`.

## Як пояснити різницю між збоями

- **DNS:** ім'я не перетворилося на IP-адресу; перевіряються DNS-записи й резолвер.
- **Connection refused:** вузол відповів одразу, але порт не слухається; перевіряються процес, порт і port mapping.
- **Timeout:** явної відповіді немає; перевіряються firewall, маршрут, навантаження і зависання сервісу.
- **Certificate:** TLS-з'єднання відхилене через недійсний сертифікат; перевіряються строк дії, ланцюжок довіри й ім'я домену.
- **Unexpected status:** HTTP-відповідь отримана, але код не той; перевіряються маршрут, health endpoint і стан застосунку.
- **Slow response:** код правильний, але перевищено поріг часу; перевіряються ресурси, база даних і зовнішні залежності.

`Connection refused` і `timeout` потребують різних дій: у першому випадку вузол доступний і проблема зазвичай біля сервісу або порту; у другому місце втрати відповіді невідоме, тому потрібна також мережева діагностика.

## Коди виходу

| Код | Значення |
|---:|---|
| `0` | усі цілі здорові |
| `1` | знайдено проблемну ціль |
| `2` | помилка конфігурації |
| `3` | не вдалося створити журнал або JSON-звіт |

Коди виходу потрібні для CI/CD, планувальника або іншого скрипта: вони дозволяють автоматично відрізнити успіх від конкретних категорій помилок.
