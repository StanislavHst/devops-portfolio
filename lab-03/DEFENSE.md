# Лабораторна робота №3 — монітор доступності API

## Завдання 2. Результат роботи

Реалізовано консольний інструмент [api_monitor.py](api_monitor.py), який перевіряє HTTP/HTTPS endpoint'и, визначає причину збою, зберігає результати та надсилає сповіщення у Discord.

Зміни внесено до особистого репозиторію `devops-portfolio` через окрему гілку та [pull request №15](https://github.com/StanislavHst/devops-portfolio/pull/15), злитий у `main`.

## Реалізація вимог

| Вимога | Реалізація |
|---|---|
| Конфігурація цілей | [config/api-monitor.json](config/api-monitor.json): URL, очікуваний HTTP-код, тайм-аут і поріг часу відповіді |
| Довідка | `--help`: призначення, усі параметри та приклад запуску |
| Перевірка параметрів | Перевірка наявності файла, коректності JSON і значень полів |
| Типи збою | DNS, відхилення з'єднання, тайм-аут, сертифікат, несподіваний HTTP-код, повільна відповідь |
| Повторна спроба | Рівно одна повторна спроба для DNS, відхилення з'єднання, тайм-ауту та помилки сертифіката |
| Журналювання | Час, ціль, статус, тривалість, тип збою, кількість спроб і результат надсилання сповіщення |
| Структурований результат | JSON-звіт із підсумком запуску та результатом кожної цілі |
| Сповіщення | Окреме Discord-повідомлення для кожної проблемної цілі з назвою, типом збою, деталями й URL |
| Секрети | Webhook передається через `DISCORD_WEBHOOK_URL`; локальне сховище зашифроване Windows DPAPI поза репозиторієм |
| Автоматичні тести | [tests/test_api_monitor.py](tests/test_api_monitor.py): 8 тестів |

Журнали `logs/` і звіти `reports/` створюються під час запуску та ігноруються Git.

## Вибір технічних рішень

**Python і стандартна бібліотека.** `argparse` забезпечує командний інтерфейс, `urllib` — HTTP-запити, `socket` і `ssl` — розпізнавання мережевих і TLS-помилок, `logging` — журнал, `json` — конфігурацію та звіт. Сторонні пакети не потрібні.

**JSON-конфігурація.** Адреси та пороги змінюються без редагування коду. Формат підтримується стандартною бібліотекою Python.

**Одна повторна спроба.** Короткочасна мережева помилка перевіряється повторно. Несподіваний HTTP-код і повільна відповідь фіксуються одразу, оскільки відповідь сервера вже отримана.

**Discord webhook.** Для надсилання повідомлень достатньо HTTP POST без окремого бота. Використовується особистий сервер **DevOps Lab Monitor**, канал **#general**, webhook **DevOps API Monitor**.

**Локальна PowerShell-обгортка.** [run-monitor.ps1](run-monitor.ps1) читає зашифрований секрет поточного Windows-користувача, передає його Python-процесу через змінну середовища та відновлює її попереднє значення після завершення. Шляхи обчислюються від розташування скрипта.

## Результати перевірки

Реальний запуск **10 листопада 2026 року**: перевірено 5 цілей, 1 здорова та 4 проблемні. Код виходу — `1`, що відповідає наявності навмисно заданих збоїв.

| Ціль | Результат | Спроби | Discord |
|---|---|---:|---|
| `healthy-endpoint` | HTTP 200, ціль здорова | 1 | Сповіщення не потрібне |
| `dns-failure` | `dns` — домен `.invalid` не резолвиться | 2 | Доставлено |
| `connection-refused` | `connection_refused` — закритий локальний порт | 2 | Доставлено |
| `expired-certificate` | `certificate` — прострочений сертифікат | 2 | Доставлено |
| `unexpected-status` | `unexpected_status` — HTTP 418 замість 200 | 1 | Доставлено |

Фрагмент журналу успішної доставки:

```text
target=dns-failure notification=sent
target=connection-refused notification=sent
target=expired-certificate notification=sent
target=unexpected-status notification=sent
```

Кожне повідомлення Discord містить поле `Тип збою`. До webhook-запиту додано `User-Agent: DevOpsLabMonitor/1.0`; після цього підтверджено доставку всіх чотирьох повідомлень.

Усі **8 автоматичних тестів пройдено**. Перевіряються класифікація збоїв, повторна мережева спроба, повільна відповідь, несподіваний код і тип збою в Discord-повідомленні. Мережеві запити в тестах замінено mock-об'єктами.

## Команди запуску та перевірки

З кореня репозиторію — запуск із локально налаштованим Discord:

```powershell
./lab-03/run-monitor.ps1
$LASTEXITCODE
```

Довідка, тести та результати з теки `lab-03`:

```powershell
cd lab-03
python api_monitor.py --help
python -m unittest discover -s tests -v
Get-Content logs/api-monitor.log -Tail 30
Get-Content reports/api-monitor-results.json
```

Перевірка неіснуючої конфігурації повертає повідомлення без traceback і код `2`:

```powershell
python api_monitor.py --config config/does-not-exist.json
$LASTEXITCODE
```

## Відхилене з'єднання та тайм-аут

**Connection refused:** вузол швидко відхиляє TCP-з'єднання. Типова причина — сервіс не запущений або не слухає потрібний порт; також можлива явна відмова firewall. Перевіряються процес, порт і перенаправлення портів.

**Timeout:** операція не завершується за відведений час. Причиною можуть бути втрата пакетів, блокування firewall, мережевий маршрут або зависання сервісу. Потрібні перевірка мережі, навантаження та журналів застосунку.

Ці результати ведуть до різних дій: явна відмова звужує пошук до доступності сервісу чи порту, а відсутність відповіді потребує ширшої мережевої діагностики.

## Коди виходу

| Код | Значення |
|---:|---|
| `0` | усі цілі здорові |
| `1` | знайдено проблемну ціль |
| `2` | помилка конфігурації або аргументів |
| `3` | помилка створення журналу або JSON-звіту |

Коди виходу дозволяють планувальнику, CI/CD або іншому скрипту автоматично визначити результат запуску.
