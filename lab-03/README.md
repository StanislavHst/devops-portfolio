# Лабораторна робота №3 — завдання 2: монітор Wishlist API

Монітор [api_monitor.py](api_monitor.py) перевіряє локальний [Wishlist API](https://github.com/nromanen/withlist-api), запущений у Docker із PostgreSQL та Redis. Усі **24 перевірки** містяться в одному [config/api-monitor.json](config/api-monitor.json). Усі адреси належать `127.0.0.1:8000`.

## Перевірки API

| Група | Маршрути й очікування |
|---|---|
| Стан залежностей | `/health`: 200 та JSON `status=healthy, redis=healthy` |
| Публічні дані | `/wishlists`, `/wishlists/1/items`: 200 |
| Документація | OpenAPI, Swagger, ReDoc, OAuth redirect: 200 |
| Авторизація | Профіль, особисті списки, історія статусів без токена: 401 |
| Відсутні ресурси | ID 0, -1, 2147483648: 404 |
| Валідація ID | Нечисловий ID списку й батьківського списку: 422 |
| HTTP-методи | GET для register, token, mark і видалення item: 405 |
| Невідомий маршрут | 404 |
| Контракт вкладеного ресурсу | `/wishlists/0/items`: очікується 404, фактично 200 |
| Демо невідомого маршруту | Навмисне очікування 200, фактично 404 |
| Демо захищеного профілю | Навмисне очікування 200, фактично 401 |
| Демо швидкості health | Навмисно занижений поріг 0.1 мс |

Склад: **20 звичайних**, **1 контрактна** та **3 демонстраційні** перевірки. Для кожної задані назва, URL, очікуваний код, тайм-аут і поріг часу відповіді.

`check_kind` — `monitoring` (типово), `contract` або `demonstration`. Категорія потрапляє у звіт і Discord; демонстрації мають префікс **[ДЕМОНСТРАЦІЯ]** у повідомленні.

Очікувані 401, 404, 405 і 422 у звичайних перевірках означають правильну поведінку API. **Три демонстрації навмисно не відповідають справній поведінці API. Це демонстрація спрацювання монітора, а не баги авторизації, маршрутизації чи підтверджена проблема швидкості Wishlist.**

Контрактна перевірка виявляє неузгодженість: `/wishlists/0` повертає 404, а `/wishlists/0/items` — 200. Очікування 404 для вкладеного ресурсу є обраним правилом контракту, а не підтвердженою вимогою автора API. ID 0 відсутній у поточній локальній базі.

## Запуск

Потрібні Python 3.10+ і Docker Desktop. Сторонні Python-пакети не використовуються.

На цьому комп'ютері API запускається так:

```powershell
docker compose -f "C:\Users\stasi\OneDrive\Документы\wishlist-local\withlist-api\docker-compose.yml" up -d
```

З теки `lab-03`:

```powershell
./run-monitor.ps1
$LASTEXITCODE
```

Підтверджений результат: **total=24, healthy=20, problems=4**, код **1**, чотири доставлені повідомлення. При додаткових несправностях кількість проблем може зрости.

У підготовленому VS Code запуск **Wishlist API — 24 checks + Discord** виконується через `Ctrl+F5`. Запуск без налагоджувача не зупиняється на очікуваному коді виходу 1.

Прямий запуск — `python api_monitor.py`. Для доставки webhook має бути в середовищі процесу.

```powershell
python api_monitor.py --help
./run-monitor.ps1 -NoNotify
```

Параметри: `--config`, `--output`, `--log-file`, `--webhook-env`, `--no-notify`.

## Discord і результати

Особистий сервер **DevOps Lab Monitor**, канал **#general**, webhook **DevOps API Monitor**. Для кожної проблемної цілі надходить повідомлення з назвою, **типом збою**, категорією, деталями та URL.

Webhook береться зі змінної `DISCORD_WEBHOOK_URL`. На цьому Windows-комп'ютері він зашифрований DPAPI поза Git: `$env:LOCALAPPDATA/DevOpsLab03/discord-webhook.xml`. Обгортка передає секрет Python-процесу й відновлює попереднє значення змінної після завершення. На іншому комп'ютері потрібен власний webhook.

Стан доставки: `notification=sent` — доставлено, `failed` — помилка, `skipped` — секрет не заданий, `disabled` — явне вимкнення. Значення webhook не друкується.

```powershell
Get-Content logs/api-monitor.log -Tail 30
Get-Content reports/api-monitor-results.json
```

Журнал містить час, дію, ціль, результат, тривалість, тип збою та спроби. JSON-звіт містить час початку/завершення, підсумок і кожний результат, зокрема `check_kind` та `expected_http_status`. Звіт записується через тимчасовий файл із подальшою заміною. Журнали, звіти та Python-кеші ігноруються Git.

## Обробка збоїв і межі перевірки

Монітор розрізняє `dns`, `connection_refused`, `timeout`, `certificate`, `unexpected_status`, `slow_response`, `unexpected_body` та іншу `network_error`. Для мережевих помилок виконується рівно одна повторна спроба.

Перевірка JSON на `/health` виявляє несправний Redis попри HTTP 200. Реальне відключення Redis й доставку сповіщення перевірено; контейнер відновлено.

GET-запити не змінюють користувачів, списки й елементи. Публічні дані можуть надходити з Redis-кешу, тому їх доступність не гарантує поточного з'єднання з PostgreSQL.

Поточний JSON містить лише локальний HTTP API за IP. Він не відтворює реальну DNS-помилку чи прострочений TLS-сертифікат. Демонстрації не замінюють вимогу лабораторної про чотири різні мережеві випадки; для неї потрібне додаткове DNS/TLS-середовище.

## Коди виходу

| Код | Значення |
|---:|---|
| 0 | усі очікування виконані |
| 1 | є проблемна ціль |
| 2 | помилка конфігурації або аргументів |
| 3 | помилка створення журналу або звіту |

## Відхилене з'єднання та тайм-аут

**Connection refused** — вузол явно відхилив TCP-з'єднання. Перевіряються процес, порт, firewall і Docker port mapping.

**Timeout** — операція не завершилася за відведений час. Причиною можуть бути втрата пакетів, блокування, маршрут чи зависання сервісу; потрібна ширша мережева діагностика.
