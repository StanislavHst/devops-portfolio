# Лабораторна робота №3 — завдання 2: монітор Wishlist API

Монітор [api_monitor.py](api_monitor.py) призначений для локального [Wishlist API](https://github.com/nromanen/withlist-api) з [Wishlist UI](https://github.com/nromanen/wishlist-ui), PostgreSQL та Redis у Docker.

## Єдина конфігурація

Усі **16 перевірок** містяться в одному файлі [config/api-monitor.json](config/api-monitor.json). Кожна ціль має назву, URL, очікуваний HTTP-код, тайм-аут і поріг часу відповіді. Усі URL ведуть виключно до локального Wishlist API `http://127.0.0.1:8000`.

| № | GET-маршрут | Очікуваний код | Що перевіряється |
|---:|---|---:|---|
| 1 | `/health` | 200 | Стан API та Redis через JSON |
| 2 | `/wishlists` | 200 | Публічний список |
| 3 | `/openapi.json` | 200 | Схема API |
| 4 | `/docs` | 200 | Swagger |
| 5 | `/users/me` | 401 | Захист профілю без токена |
| 6 | `/redoc` | 200 | ReDoc |
| 7 | `/my-wishlists` | 401 | Захист особистих списків |
| 8 | `/wishlists/0` | 404 | Відсутній список з ID 0 |
| 9 | `/wishlists/not-a-number` | 422 | Валідація числового ID |
| 10 | `/wishlists/0/items` | 200 | Порожня колекція елементів |
| 11 | `/wishlists/0/items/0/statuses` | 401 | Захист історії статусів |
| 12 | `/register` | 405 | GET заборонений для реєстрації |
| 13 | `/token` | 405 | GET заборонений для входу |
| 14 | `/wishlists/0/items/0/mark` | 405 | GET заборонений для зміни статусу |
| 15 | `/wishlists/0/items/0` | 405 | GET не підтримується маршрутом видалення |
| 16 | `/__monitor_missing_route__` | 404 | Обробка неіснуючого маршруту |

Очікувані `401/404/405/422` означають правильну поведінку API в цих сценаріях. Монітор фіксує проблему, лише якщо фактичний результат відрізняється від налаштованого або відповідь надто повільна.

ID 0 використано як відсутній ресурс у поточній локальній базі. Якщо дані або контракт API зміняться, очікування потрібно переглянути. Перевірка `/wishlists` може отримати дані з Redis-кешу, тому не гарантує актуального з'єднання з PostgreSQL.

## Запуск проєкту та монітора

Потрібен Python 3.10+ без сторонніх пакетів і запущений Docker Desktop.

На цьому комп'ютері API запускається командою:

```powershell
docker compose -f "C:\Users\stasi\OneDrive\Документы\wishlist-local\withlist-api\docker-compose.yml" up -d
```

Команди монітора виконуються з теки `lab-03`:

```powershell
python api_monitor.py --help
./run-monitor.ps1
$LASTEXITCODE
```

Очікуваний результат справного проєкту: **total=16, healthy=16, problems=0**, код виходу **0**.

Прямий запуск того самого Python-файла:

```powershell
python api_monitor.py --config config/api-monitor.json --output reports/api-monitor-results.json --log-file logs/api-monitor.log
```

Параметри: `--config` — конфігурація, `--output` — JSON-звіт, `--log-file` — журнал, `--webhook-env` — назва змінної з webhook, `--no-notify` — явне вимкнення сповіщень.

## Перевірка JSON і типи збою

Для `/health` очікуються поля:

```json
"expected_json": {"status": "healthy", "redis": "healthy"}
```

Wishlist може повертати HTTP 200 при `redis=unhealthy`. Тому монітор додатково перевіряє JSON і повідомляє `unexpected_body`. Зчитується не більше 1 MiB JSON-відповіді.

Інструмент окремо обробляє `dns`, `connection_refused`, `timeout`, `certificate`, `unexpected_status`, `slow_response`, `unexpected_body` та загальну `network_error`. Для мережевих помилок передбачена рівно одна повторна спроба. Якщо повтор успішний, ціль вважається здоровою.

Обмеження поточної конфігурації: локальний API використовує HTTP та IP-адресу. Тому ця конфігурація не відтворює живу DNS-помилку чи прострочений TLS-сертифікат. Їх обробка перевіряється автоматичними тестами. Вимога умови про реальний прогін чотирьох різних мережевих випадків потребує додаткового налаштування DNS/TLS або тестового середовища; самі перевірки правильних `401/404/405/422` не замінюють ці випадки.

## Discord і секрет

Для кожної проблемної цілі надсилається окреме повідомлення з її назвою, **типом збою**, деталями та URL. Здорові цілі повідомлень не створюють.

Використовується особистий сервер **DevOps Lab Monitor**, канал **#general**, webhook **DevOps API Monitor**. Адреса webhook береться зі змінної середовища `DISCORD_WEBHOOK_URL`.

На цьому Windows-комп'ютері секрет зашифрований DPAPI та лежить поза Git у `$env:LOCALAPPDATA/DevOpsLab03/discord-webhook.xml`. Обгортка `run-monitor.ps1` передає секрет Python-процесу через середовище і відновлює попереднє значення змінної після завершення. На іншому комп'ютері задається власний webhook.

Без webhook перевірки працюють, але журнал містить `notification=skipped`. Успіх доставки позначається `notification=sent`, помилка — `notification=failed`, явне вимкнення — `notification=disabled`. Значення webhook не виводиться у журнал.

Реальне сповіщення перевірено на несправності Redis: HTTP 200 з неправильним JSON дав `unexpected_body`, повідомлення доставлено. Контейнер відновлено. Монітор не виконує CRUD-запити та не змінює користувачів, списки або елементи.

## Журнал, звіт і коди виходу

```powershell
Get-Content logs/api-monitor.log -Tail 30
Get-Content reports/api-monitor-results.json
```

Журнал містить час, дію, ціль, статус, тривалість, тип збою, кількість спроб і стан сповіщення. JSON-звіт містить час початку/завершення, підсумок та результат кожної цілі. Звіт записується через тимчасовий файл із подальшою заміною. `logs/`, `reports/` і Python-кеші ігноруються Git.

| Код | Значення |
|---:|---|
| 0 | усі цілі здорові |
| 1 | є проблемна ціль |
| 2 | помилка конфігурації чи аргументів |
| 3 | помилка запису журналу або звіту |

Доставка сповіщень перевіряється за журналом; код 1 описує стан цілей.

## Автоматичні тести

**63 тести**: 57 автономних та 6 інтеграційних із запущеним Wishlist. Інтеграційний тест проходить через усі 16 записів єдиного JSON. Автономний набір перевіряє валідацію конфігурації, типи збою, retry/recovery, часові пороги, JSON, звіти, коди виходу та Discord. HTTP-поведінка також перевіряється справжнім локальним тестовим сервером.

```powershell
# Без залежності від Docker: 57 тестів і 6 пропущених інтеграційних
python -m unittest discover -s tests -v

# З працюючим Wishlist у Docker: усі 63
$env:WISHLIST_LIVE = "1"
python -m unittest discover -s tests -v
Remove-Item Env:WISHLIST_LIVE
```

Автоматичні тести не надсилають повідомлення у Discord. Початковий файл із 8 тестами збережено без змін.

## Відхилене з'єднання та тайм-аут

**Connection refused** — вузол явно відхилив TCP-з'єднання: сервіс не слухає порт або firewall повернув відмову. Перевіряються процес, порт і Docker port mapping.

**Timeout** — операція не завершилася за відведений час: можливі блокування, втрата пакетів, проблеми маршруту чи зависання сервісу. Потрібна ширша мережева діагностика, перевірка навантаження та журналів.
